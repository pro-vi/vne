# dopbase vs vne — secret boundaries from opposite architectures

## vne's thesis, in vne's own terms

vne is a local desktop env-file workbench. Its safety bar (docs/THREAT_MODEL.md:3): opening, inspecting, and editing env files must not move secret contents outside the user's machine. The load-bearing boundary is **output hygiene** — CLI JSON payload-free by default, `--values` opt-in for classifier-approved values, values never in argv or error echoes, atomic same-directory writes, git exposure states. Explicit non-goal (THREAT_MODEL.md:58): *vne is not a secrets manager*. dopbase is exactly the thing that non-goal excludes — which makes this a study of where the boundary lessons transfer and where the architectures are structurally opposed.

## What dopbase is (corrected record)

Self-hosted team secrets manager: Rust axum server + CLI + Vue admin UI in one executable, SQLite + config + master key under `~/.dopbase`, model Project → Environment → Secrets, default bind 127.0.0.1:8840, plain HTTP (self-hosters own TLS). Two README framing corrections from the CHANGELOG [D]: AI service accounts shipped in **0.1.0**, not 0.1.6; factory reset shipped 0.1.2/0.1.5 — the crash-safe marker is code-verified but not changelog-attributed. And "24 SQL files" is 12 reversible migration **pairs** — a real `sqlx::migrate!` system exists; what's true is that 0.1.0 requires a fresh data directory, pre-0.1.0 DBs and `.dop` backups unsupported.

## Pattern merge (clustered by intent)

**Intent: keep values away from agents and transcripts**
- dopbase: server-side role gate + hashed tokens + TTY-gated interactive re-auth (client.rs:586-609) + audit events carrying names/counts only (verified by disconfirming grep — the docs' "never contain the plaintext" claim held).
- vne: structural withholding in every output channel.
- Conflict worth naming: dopbase's gate has a hole the docs don't discuss — `run` uses `any_authenticated_client` with no confirmation, so an agent holding the developer's same-machine session can bulk-fetch every value via the runtime endpoint. vne's invariant doesn't have this shape of hole because it promises less.

**Intent: durable local state without partial writes** — converged: both use exclusively-created temp file, sync, atomic rename, owner-private permissions. dopbase adds the durable-intent-marker pattern for multi-step destructive ops (reset), replayed at startup (server.rs:48-72).

**Intent: .env fidelity** — converged: dopbase's strict parser and the valueless layout (comments/blank lines/ordering/export preserved server-side, values stripped, `KEY=` slots refilled at edit time, inline comments relocated) are dopbase rebuilding vne's core competency as a server artifact — its own quiet admission that developers won't give up the file's *shape*.

**Intent: survive concurrency** — divergent: dopbase versions + revision-hashes; vne is one read, one transform, one atomic write, last-write-wins.

## Transfer assessment

🟢 **Transfers directly**
- *Metadata/values split as output vocabulary* — vne already lives this; dopbase is independent confirmation the split is the right default for any secret-bearing CLI.
- *TTY-gate on raw output* — vne's `format --dry-run` (refuse piped stdout exit 2, interactive `y`) and dopbase's reveal gate (TTY + password re-POST) are the same pattern at different strengths. Nothing to change; validation.
- *Write-time changed-underneath guard — already shipped in vne, stronger than dopbase's.* VNE-SEC-013 `atomic_write_metadata_if_unchanged` (src-tauri/src/lib.rs:3893) re-checks content bytes **and** inode identity (dev, ino) at persist time; every mutating call site passes the read bytes (src-tauri/src/cli.rs:667 for `add`; lib.rs:924 desktop save, 953 missing-key insert, 1586 `copy`, 1789 `set`, 1856 `rm`, 1984 `rename`, 2104 `example`). dopbase's SHA-256 collection revision (secrets/service.rs:265-403) is the same intent convergently, without the identity check. Remaining residual on both sides: the non-cooperating-writer TOCTOU window between check and rename — already documented at THREAT_MODEL.md:69.

🟡 **Needs adaptation**
- *Credential-bound local crypto* (HKDF(local key, credential, server URL) — cache/store.rs:473-487). The only pattern that approximates "agent can't open it" without a server. For current vne this is 🔴 — it contradicts the no-store, no-credentials thesis. It becomes 🟡 only if vne ever grows a vault-adjacent feature, which is a product decision, not a technical one.

🔴 **Doesn't transfer**
- *Server-side roles/revocation/re-auth* — needs a trusted process holding identity and ciphertext apart from the requester (H1). In a local tool, any withholding is a rendering choice the agent can route around by reading the file.
- *Envelope encryption, backups, migration machinery* — vne owns no storage; this is the non-goal working as intended.

## Insights

**Validated directions** (things vne does that dopbase converged on independently): atomic-write discipline; parser edge-case coverage (export prefix, inline comments, duplicates rejected with line numbers); metadata-first output; refusing value materialization where a name suffices.

**Gaps to close**: none found — see Post-promotion verification. The write guard this synthesis originally proposed as missing was already shipped (VNE-SEC-013). Everything dopbase does better (crypto, audit, recovery) lives on the other side of vne's non-goal.

**Differentiation to preserve**: vne's absolute invariant. dopbase cannot promise "values never appear in output" — its best promise is "a human was present when they did." For agent-era tooling the absolute invariant is the rarer and stronger property; it is also the source of vne's documented residual (dispositions disclose value equality), which is the honest price of it.

**Vocabulary worth adopting**: "metadata/values split" as a name for vne's output policy; "durable intent marker" if a destructive multi-step op ever lands.

**Market signal (H3)**: dopbase's background.md is an anti-.env manifesto — .gitignore "does not stop an IDE extension… or a local agent from scraping context." Its answer is env-at-exec. vne's position is the complement: the files exist, developers keep them, and the editor is where hygiene happens. dopbase's own concessions (the valueless layout, the strict parser) show the artifact's *shape* survives even in its replacement — vne's fidelity work is not made obsolete by the injection model, it is imported by it.

## Post-promotion verification (2026-09-15, vne source read)

The synthesis's transfer candidates were verified against vne's code the same day. Results:

1. **Write guard: already shipped, stronger than proposed.** `atomic_write_metadata_if_unchanged` (src-tauri/src/lib.rs:3893, VNE-SEC-013) — content bytes + inode identity re-check at persist time, wired through every mutating command (citations in the 🟢 section above). The original "gap to close" claim came from misreading THREAT_MODEL.md:69: that residual describes the *non-cooperating-writer* TOCTOU window (after the guard, before the rename), not the absence of a guard between cooperating vne invocations. dopbase has the same window.
2. **Parser checklist: no gap.** dopbase's strict importer (app/src/cli/dotenv.rs) against vne's lossless parser, edge by edge: unterminated quotes → vne emits the `"quoted value is not closed"` diagnostic (lib.rs:2748) instead of bailing; duplicates → vne reports occurrences with line numbers and requires an occurrence choice instead of bailing; unquoted inline comments → same whitespace-then-`#` rule on both sides (`extract_inline_comment`, lib.rs:4243, vs dotenv.rs:67); `export` prefix, quote escape handling, and multiline values are covered by vne's test list and `fixtures/adversarial-dotenv` (quote-comments, duplicates-invalid, multiline). Editor semantics subsume importer semantics here.
3. **Valueless layout: no code implication.** It is server-side storage of the file's shape without values (migration 0009); vne's counterpart is the file itself plus additive `example` sync. Positioning insight only.
4. **The `run`-asymmetry lesson is absorbed by design.** dopbase's hole — `run` bulk-fetches values with no confirmation while `--reveal`/`export` demand interactive re-auth — has no vne analog because vne's invariant is structural: no JSON output path can emit a secret-classified value, so there is no gate to route around.

Net: every transfer candidate from this research is either already shipped in vne (convergent validation), correctly a non-adoption, or a positioning fact. No code change follows from this study.

## Addendum — sandboxing changes the boundary math (2026-09-15, from discussion; inferred, not code-verified)

H1's pessimism assumes the agent and the user share a filesystem, so any local withholding is a rendering choice the agent routes around by reading the file. Agents running sandboxed (seatbelt, containers) break that assumption: the OS restores a boundary between requester and data without a server, which makes a local tool's structural withholding *enforceable* again and strengthens — not weakens — the local-only thesis. In that world dopbase also reads as a reasonable personal-dev tool: its metadata-only AI accounts compose with sandboxed agents, and its value gate stays for the human path. No vne code implication today; this is a positioning fact worth keeping in view when the THREAT_MODEL.md non-goals are next revisited.
